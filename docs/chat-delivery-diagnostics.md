# 聊天发送诊断

原先只有 QQ 确认发送成功或待审核后才保存问答，因此平台拒绝时无法找回
生成的回答。现在将“参与对话的历史”与“用于排错的发送记录”分离。

## 保存流程

1. 模型生成后、实际发送前，在现有聊天 SQLite 数据库新增的
   `chat_deliveries` 表中保存一次发送记录。
2. 保存的是最终准备发给 QQ 的文本，已经过链接清理；不保存系统提示、
   原始网页、思考内容或整段聊天历史，也不额外保存失败提问。
3. 成功发送且正常历史写入成功后，删除临时诊断；成功历史保留原有策略。
4. 发送异常、未确认结果、待审核或历史写入异常，保留诊断供管理员查看。

状态说明：

| 状态 | 含义 |
| --- | --- |
| sending | 发送尚未结算，也可能因进程中断而未确认；不能直接认定未送达 |
| failed | 发送抛出异常；不自动重发 |
| unknown | 超时、取消或 QQ 未确认结果；不自动重发 |
| pending | 平台返回待审核，不加入模型上下文 |
| not_sent | 回答超过发送长度限制，没有请求 QQ |
| sent_unrecorded | QQ 已确认发送，但普通历史写入失败；不能重发 |

诊断保存模型名、token 用量、异常类型和创建时间。只保存 SDK 明确返回的
`type:business, code:..., msg:...` 业务诊断文本，不保存任意异常正文，避免
连接异常中的认证信息泄露。SDK 丢失的 HTTP 错误码、trace_id 无法凭空恢复，
仍需要结合现有日志的时间定位。

## 在 admin-panel 查看

更新代码、重启 bot 并刷新面板后，“聊天诊断”分类提供：

- 聊天发送异常列表：最近的记录 ID、状态和元数据；不返回回答或错误正文。
- 聊天发送异常详情：输入记录 ID，确认后查看最终发送文本和可用错误信息。

两者都使用原有管理令牌鉴权，不提供普通频道查询命令。详情属于可能敏感的
内容，接口禁止缓存，请勿将结果直接转发到公共频道。聊天未启用时不创建
ChatService，面板中的诊断操作也不可用，可由服务器管理员直接检查数据库。

这不会恢复更新前已失败且从未保存的回答，需要更新后重新触发才能留存。

## 保留、清理和重置

- 逻辑保留期固定为 24 小时，过期记录不通过管理接口返回。
- 单条回答最多保存 10000 字符，`answer_chars` 是原长度，可据此判断截断。
- 最多保留最新 1000 条；超过容量时，较旧诊断可能提前删除。
- 写入和查询时清理，聊天运行时另有每分钟后台清理；关闭 bot 或聊天功能
  后不保证即时物理删除，下一次运行清理或查询时再处理。
- `/聊天 /reset` 同时清除当前频道当前用户的上下文及诊断。旧请求结束时
  只更新原记录，不会重新插入被清除的文本；其他用户、频道不受影响。
- 普通日志不输出回答正文。诊断数据库写入失败时记录元数据错误，不因此
  重发消息；失败回答仍然不会加入后续聊天上下文。

数据库会在原有初始化时幂等创建新表，不需要删除旧库、迁移旧聊天记录或
修改 `chat.yaml`。回滚代码不影响旧表，但新诊断表会留下且不再自动清理，
应由服务器管理员按需要处理；备份中的历史数据不受本地清理影响。
