# 实验性 QQ 频道消息来源发现

本功能基于当前账号的实测行为，不是腾讯承诺的稳定协议：同 guild 的近期
普通用户消息 ID 可能被用于另一子频道的回复。查询成功不保证发送成功，
也不能证明平台内部主动消息计数完全不变。

## 默认状态

`config/reply_sources.yaml` 的两个开关默认均为 `false`：

- `enabled`：允许手动登记、有限查询和缓存配置范围内的消息元数据。
- `automatic_forwarding`：允许直播通知使用来源池，并在来源不足时有限查询。

第二个开关要求第一个也已开启。只开启手动实验时，不改变原有直播通知的
发送方式；原来的主动通知仍由 `config/live_forwarding.yaml` 控制。

## 手动验证步骤

1. 在 `config/reply_sources.yaml` 中设置 `enabled: true`，保持
   `automatic_forwarding: false`。
2. 填写 guild 与来源、目标子频道白名单。例如：

   ```yaml
   guilds:
     - guild_id: "15913006732425380356"
       source_channel_ids: ["723086974"]
       target_channel_ids: ["723086974"]
   ```

   按需替换 ID；来源和目标可以不同，但必须属于同一 guild。不是自动扫描
   该 guild 的所有频道，返回的频道列表仅用于验证白名单。
3. 重启 bot，刷新 admin-panel，在“实验消息来源”里执行“登记消息来源种子”：
   填 guild、来源子频道和一个已知真实消息 ID。此操作会查询频道列表、
   查询种子，核对返回结果，不发送消息。
4. 执行“有限探测消息来源”。模块从已确认序号向后查询有限候选，保存
   返回的真实 ID；不会将构造 ID 直接作为回复来源。
5. 使用“查看消息来源状态”观察来源 ID、年龄、使用次数、暂停状态和冷却。
   该操作不请求 QQ。来源列表包含已使用的来源，不代表每条都仍可用。
6. 将新鲜来源的真实 `message_id` 复制到原“发送频道消息”的 `msg_id` 中，
   在测试频道手动验证。手动发送不经过来源池的预留机制，应避免与自动
   转发同时使用同一来源；测试完成后重新登记新种子再启用自动模式。

普通用户作者需要返回 `bot: false`；机器人或作者类型不明确的消息只能
推进定位种子，不能作为回复来源。过期消息也可以作为定位种子，但不能
用于发送。未来版本的 ID 格式无法解析时会拒绝，不影响普通命令执行。

## 自动转发

手动验证完成后，可设置 `automatic_forwarding: true` 并重启。直播转发本身
仍需要在 `config/live_forwarding.yaml` 中开启、配置通知目标，并按需要退出
`dry_run`。自动模式流程：

1. 按原有主播、金额和目标子频道规则生成投递。
2. 从目标对应 guild 的池中预留一个新鲜来源，再携带其真实 ID 发送。
3. 无来源时，投递保持 pending，并触发后台有限发现；不自动降级主动发送。
4. 原有通知 `max_event_age_seconds` 到期后转为 expired，不无限积压。

自动模式下所有启用的直播通知目标都必须配置到目标白名单中。未配置的
目标会保持 pending 直到过期，而不是悄悄使用主动额度。

每条来源默认全局使用一次，而不是每目标频道一次；最大可调为五次，
只是本地保守上限，不表示官方承诺频道支持五次。所有目标共享来源预留，
同一来源不会被并发占用。调用前先将使用情况写入本地 SQLite，进程重启、
超时或结果不明不会恢复已经预留的次数。
本实现面向单个 bot 进程，不支持多个进程同时共享这个 SQLite 来源池。

明确的来源拒绝将停用来源、记录该通知失败；不立即换来源重发。发送超时
则将投递记为 unknown，防止重复通知。现有 botpy 的部分异常只保留错误文本、
丢弃业务错误码，所以这类异常不猜测是否可安全重试。审核响应也不重发。

机器人实际收到的白名单 @ 消息，以及直播转发成功返回的消息元数据，也
会补充定位种子；机器人自己发送的消息不会成为可用回复来源。

## 查询预算与限制

- 每轮最多 10 次单条消息探测，频道列表验证另计，但也共享全局限速。
- 所有发现读取串行，默认最多每分钟 60 次、轮次之间至少 15 秒。
- 每个来源频道只在已确认序号之后最多 100 个位置内轮转；没有确认到更新
  消息时，空缺位置会在后续轮次重查。一旦确认到更新序号，则从新种子继续，
  不保证补齐旧位置的全部消息，也不把“查过”当成“消息已经存在”。
- 不在未知范围内无限向前跳跃。种子太旧、序号距离超过上限时，需要人工
  提供较新的种子，或等待机器人收到该来源频道的真实 @ 消息。
- 来源有效期默认按返回的真实 `timestamp` 控制在 270 秒以内；不使用 ID
  内构造的时间戳续期，也不修改来源、目标的 guild/channel。
- 404 跳过该位置；权限错误暂停来源；429 停止本轮并退避至少 60 秒；
  其他错误、超时、无效响应停止本轮。通过重新登记并成功验证恢复暂停来源。

只有待发通知缺少可用来源时才自动查询；没有通知不会后台持续扫描。
手动登记不受轮次冷却限制，但仍共享串行请求间隔。元数据中的未知字段
不会被输出成消息正文。

## 存储、回滚与测试

### 发送日志

频道 `post_message` 使用现有 botpy 的 INFO 日志，不需要开启 SDK DEBUG：

- `QQ channel send start`：记录本地 `attempt` 编号、目标 `channel_id`、
  `mode` 和本次使用的来源 `msg_id`。
- `QQ channel send end`：用相同 `attempt` 关联结果，记录 `status`、
  返回的新 `message_id`，以及响应中可用的业务错误码。异常只记类型，
  不额外记录错误正文。取消请求记为 `cancelled_unknown`。
- `Live notification send`：额外关联直播事件 `event_id` 和来源
  `source_channel_id`，便于追踪跨子频道来源。

`mode=proactive` 表示未携带回复来源；`mode=reply` 表示携带 `msg_id`；
`mode=event_reply` 表示只携带 QQ 事件 `event_id`。这些描述的是请求方式，
不是平台主动额度的记账结果。日志不包含消息正文、图片内容或认证令牌。
日志中的 ID 会限制长度并转义控制字符，不会更改实际请求参数。

### 存储和回滚

仅 `reply_sources.db` 保存种子 ID 和使用状态，已加入 Git 忽略规则。模块
不保存消息正文或作者资料；原有 SDK 的调试日志可能记录 QQ 响应，测试时
不要为了排查本功能随意开启包含消息正文的 SDK 调试日志。

关闭自动实验：设置 `automatic_forwarding: false` 并重启，恢复原有发送路径。
完全关闭：再设置 `enabled: false`；此时不打开实验数据库，不做发现查询。
若还要停止所有直播通知，应另行关闭直播转发配置，不能只关闭本实验。

离线测试覆盖编解码、非法输入、白名单、同 guild 共享、固定扫描范围、
空缺重查、冷却、权限暂停、来源过期、重启预留、HTTP 管理入口和发送歧义。
普通测试均使用模拟 QQ 响应，不会调用真实 QQ 接口。
